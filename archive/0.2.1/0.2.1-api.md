If I created an API key in my https://sonarcloud.io account, do I only have access to my own issues  (i.e. https://sonarcloud.io/project/issues...) or can I also fetch other people's sonar issues (i.e. curl)

---
No, you cannot fetch issues from other people's projects without authorization. A SonarCloud User Token grants **exactly the same permissions as the user account that created it**.

This means you can only access and fetch issues from projects and organizations that your user account is a member of and has the necessary permissions to view.

### 🔑 How Token Access Works

*   **Full User Permissions**: Your API token acts as a key that has the exact same access as your login. If you can't see a project in the SonarCloud web interface, you won't be able to access its data via the API.
*   **Project Visibility Matters**: The distinction between public and private projects is critical:
    *   **Private Project**: Access is strictly enforced. The token must be associated with a user account that is a member of the project's organization and has the specific **'Browse'** permission or higher.
    *   **Public Project**: While it is often possible to fetch some data from public projects without a token, using one is still generally required for full API access, and permissions are still enforced.

### 💡 Best Practices

When using the SonarCloud API, it's a good security practice to follow the principle of least privilege:

*   **Prefer Project Tokens for CI/CD**: For automated tasks like running analyses, use **Project Analysis Tokens**. Their access is scoped to a single project, which minimizes risk if compromised.
*   **Avoid Scoped Organization Tokens for API Access**: Note that **Scoped Organization Tokens (SOTs)** are designed for running analyses and will **not work** for general API queries [5†L9-L10].

### 🔧 How to Check Your Access

The most reliable method to know which projects your token can access is to simply call an API endpoint and check for a successful response.

#### 🐚 Using `curl` to Verify Access

Here’s a practical example of how to query the `api/issues/search` endpoint with your token.

```bash
# Replace placeholders with your actual values
curl -H "Authorization: Bearer YOUR_TOKEN_HERE" \
     "https://sonarcloud.io/api/issues/search?projectKeys=YOUR_PROJECT_KEY"
```

*   **Successful (200 OK)**: A successful request proves you have access to that project.
*   **Not Found (404)**: Typically indicates you lack the 'Browse' permission for the project, or the project key is incorrect.
*   **Forbidden (403)**: Indicates your token is valid, but your user account does not have the required permission to access the requested resource.

As a best practice, **do not hardcode tokens in scripts**. Use environment variables (e.g., `SONAR_TOKEN`) to keep them secure.

Your hunch is correct: a contributor's personal SonarCloud API token cannot access your project unless they are explicitly granted permissions. For your specific case of allowing open-source contributors to fetch issues from a public project, the real answer is encouraging—SonarCloud's API **does** allow unauthenticated access to issue data for public projects.

## 🔓 Unauthenticated Access Is Possible for Public Projects
The key distinction is between "private" and "public" projects. Multiple official sources confirm that for **public** projects, the SonarCloud API endpoints that read data—such as `api/issues/search`—can be accessed **without any authentication token**.

* **Official Documentation:** The SonarCloud documentation directly states that "You can view issues on all public projects" and this permission is enforced at the API level, not just the UI.
* **Community & Historical Data:** A SonarCloud employee clarified that "only the public projects of your organization will be returned" for unauthenticated requests to the search API. Additionally, as recently as May 2025, the API worked without authentication for public project data, though a subsequent bug was quickly resolved.

This means your plan is viable. A contributor could run a `curl` command like the one below and receive the issue data without needing a token of their own.

```bash
curl "https://sonarcloud.io/api/issues/search?projectKeys=YOUR_PUBLIC_PROJECT_KEY"
```

## 🛠️ The Smart Way to Share Issue Data
While the above works, here are a few practical ways to streamline the process:

1.  **Create a Dedicated Read-Only Bot Account**: For absolute clarity and control, you can create a dedicated account in SonarCloud (e.g., `yourproject-bot`) with only "Browse" permissions on your project. Generate a **Project Analysis Token** for this bot and share it publicly (it's safe, as its permissions are limited).
2.  **Automate with a Script**: Provide a simple shell script in your repository's `README` that contributors can run. This script would execute a `curl` command that fetches and filters issues (e.g., only "BUG" or "VULNERABILITY" types).
3.  **Explore CLI Tools**: Some community-driven tools are designed to work with SonarCloud's API and may have flags like `publicSonar: true` that don't require a token for public projects.
4.  **Leverage Webhooks**: For real-time integration, you could set up a webhook that automatically posts new SonarCloud issues to a public Slack channel, Discord server, or a GitHub issue tracker. This would notify contributors as soon as new findings are available.
