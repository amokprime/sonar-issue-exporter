Great question — and yes, this project would absolutely benefit from offering `uv` or `venv` as installation options. Here's my analysis based on the codebase:

## Current State

The project (`sonar-issue-exporter`) currently instructs users to install via:

```bash
pip install git+https://github.com/amokprime/sonar-issue-exporter.git
```

This installs `requests` and `pyperclip` (plus the optional `html2text`) directly into the user's **global/site Python environment**. The dependency footprint is small (6 packages total in `requirements.txt`), but the principle still matters — especially for users who manage multiple Python projects or are particular about their system environment.

## Why `uv` or `venv` Would Help

| Concern | How `uv`/`venv` Solves It |
|---|---|
| **Polluting the system Python** | Isolates `requests`, `pyperclip`, etc. inside a project-local environment |
| **Version conflicts** | Prevents clashes if the user already has a different `requests` version globally |
| **Clean uninstall** | Delete the venv folder — no orphaned packages left on the system |
| **Reproducibility** | `uv.lock` or pinned `requirements.txt` ensures exact versions every time |
| **Security-conscious users** | Some users are wary of `pip install` touching system packages |

## Recommendation: Support Both `uv` and `venv`

Given the project's target audience (developers using SonarCloud, comfortable with terminals), I'd suggest offering **three installation paths** in the README:

### 1. `uv` (Recommended — fastest, modern)
```bash
# One-liner install into an isolated environment
uv tool install git+https://github.com/amokprime/sonar-issue-exporter.git

# With optional markdown support
uv tool install "sonar-issue-exporter[markdown] @ git+https://github.com/amokprime/sonar-issue-exporter.git"
```

`uv tool install` is ideal here — it creates an isolated environment automatically, exposes the `sonar-export` and `sonar-watch` CLI entry points, and doesn't touch the system Python at all. It's the spiritual successor to `pipx`.

### 2. `venv` (Batteries-included, no extra tool needed)
```bash
python -m venv .venv
# Activate:
# Windows: .venv\Scripts\activate
# Linux/Mac: source .venv/bin/activate
pip install git+https://github.com/amokprime/sonar-issue-exporter.git
```

This requires no extra tool but adds a manual activation step. Good for users who want full control.

### 3. Bare `pip` (Keep as-is for quick-start)
Keep the current instructions as the "quick and dirty" option for users who don't care about isolation.

## What Would Need to Change in the Repo

Very little — the project is already well-structured:

1. **`pyproject.toml` is already correct** — it has `[project.scripts]` entry points, proper dependencies, and `[project.optional-dependencies]`. Both `uv` and `venv` will work with it as-is.

2. **Add a `uv.lock` file** (optional but nice) — running `uv lock` in the repo generates a lockfile for deterministic installs.

3. **Update the README** — add the `uv` and `venv` installation paths alongside the existing `pip` instructions. This is the main change.

4. **No code changes needed** — the Python source (`export_sonar_issue.py`, `watch_clipboard.py`) doesn't need any modifications.

## One Watch-Out: `pyperclip`

Inside a venv, `pyperclip` itself is isolated, but it still calls out to whatever system clipboard tool exists. This works fine on Windows (built-in) and macOS (built-in), but Linux users need to ensure `xclip` or `xsel` is installed at the OS level regardless of Python environment isolation. Worth a small note in the README.

That's a known friction point — `uv tool install` uses `git` under the hood, and GitHub sometimes prompts for credentials even on public repos depending on your git configuration, network setup, or if you've hit rate limits. Here are the practical workarounds, from easiest to most robust:

---

## Option 1: Clone first, then install locally (Simplest fix)

This avoids the git-over-HTTPS credential prompt entirely:

```bash
git clone https://github.com/amokprime/sonar-issue-exporter.git
cd sonar-issue-exporter
uv tool install ".[markdown]"
```

No authentication prompt because `git clone` of a public repo doesn't require it (and if your git is already authenticated for GitHub, it definitely won't). `uv` then installs from the local directory instead of reaching out to GitHub again.

## Option 2: Use the SSH URL instead

If you have SSH keys set up for GitHub (which avoids password prompts entirely):

```bash
uv tool install "sonar-issue-exporter[markdown] @ git+ssh://git@github.com/amokprime/sonar-issue-exporter.git"
```

## Option 3: Use a GitHub Personal Access Token (PAT)

If you want to keep the one-liner but avoid the interactive prompt:

```bash
uv tool install "sonar-issue-exporter[markdown] @ git+https://<YOUR_PAT>@github.com/amokprime/sonar-issue-exporter.git"
```

Replace `<YOUR_PAT>` with a fine-grained token that has read access to public repos. You can generate one at **GitHub → Settings → Developer settings → Personal access tokens**.

## Option 4: Suppress the prompt (and let it fail if auth is truly needed)

```bash
GIT_TERMINAL_PROMPT=0 uv tool install "sonar-issue-exporter[markdown] @ git+https://github.com/amokprime/sonar-issue-exporter.git"
```

This tells git to fail silently instead of prompting. For a public repo, it should still succeed — the prompt you're seeing is likely coming from git's credential helper trying to authenticate unnecessarily.

---

## Why This Happens

It's usually one of these:

1. **Git credential helper is configured** — your system git has a credential manager that intercepts HTTPS connections to GitHub and asks for login, even for public repos.
2. **You've hit GitHub's unauthenticated rate limit** — after too many unauthenticated git operations, GitHub starts requiring auth.
3. **Corporate proxy or firewall** — some networks inject auth prompts for all HTTPS traffic.

## What I'd Recommend for the README

Since this is a real usability issue, the project should update the README to offer the **clone-then-install** approach as the primary method, with the one-liner as an alternative:

```python
def find_env_file() -> Optional[Path]:
    """Find the .env file: current directory → script directory → home directory."""
    cwd_env = Path.cwd() / ".env"
    if cwd_env.exists():
        return cwd_env
    script_env = Path(__file__).parent / ".env"
    if script_env.exists():
        return script_env
    home_env = Path.home() / ".env"
    if home_env.exists():
        return home_env
    return None
```

**Change 2:** Detect subprocess failures in `watch_clipboard.py`:

In `DownloadTracker._display_loop()`, change the completion check to also look at the return code:

```python
def _print_completed(self, entry: dict):
    """Print the checkmark or cross line for a completed download."""
    url = entry["url_short"]
    ret = entry["process"].returncode
    if ret == 0:
        sys.stdout.write(f"\r  ✓ {url}{_CLEAR_EOL}\n")
    else:
        sys.stdout.write(f"\r  ✗ {url} (exit {ret}){_CLEAR_EOL}\n")
    sys.stdout.flush()
```

```python
def api_get(endpoint: str, params: dict, token: Optional[str] = None) -> dict:
    headers = {}
    if token:
        headers["Authorization"] = f"Bearer {token}"
    url = f"{BASE}/{endpoint}"
    resp = requests.get(url, params=params, headers=headers)
    try:
        resp.raise_for_status()
    except requests.exceptions.HTTPError as e:
        print(f"\nAPI ERROR: {e}", file=sys.stderr)
        print("Response body:", resp.text, file=sys.stderr)
        if resp.status_code == 401:
            print("Hint: this project may require authentication. Set BEARER_TOKEN in .env.", file=sys.stderr)
        raise
    return resp.json()
```

>The tool searches for `.env` in the current directory, then the script directory, then your home folder.

Where is the "script directory" for the tool run in terminal from an arbitrary folder? Does it remember the git cloned folder?

---
No, it doesn't remember the clone folder. When installed via `uv tool install`, the code is copied into uv's managed environment:

```
~/.local/share/uv/tools/sonar-issue-exporter/lib/python3.12/site-packages/
```

So `Path(__file__).parent` — the "script directory" — resolves to that buried site-packages path, not your clone. The clone folder is irrelevant at runtime; uv built a wheel from it and installed the result.

This means the "script directory" fallback is effectively useless for `uv tool` users. The actual search order is:

| Priority | Location | Useful? |
|---|---|---|
| 1 | Current directory | Yes — if you `cd` to a project with its own `.env` |
| 2 | `~/.local/share/uv/tools/.../site-packages/` | No — no user will ever put a `.env` there |
| 3 | Home directory | Yes — the reliable default |

You could simplify `find_env_file()` to just skip the script directory entirely:

```python
def find_env_file() -> Optional[Path]:
    """Find the .env file: current directory, then home directory."""
    cwd_env = Path.cwd() / ".env"
    if cwd_env.exists():
        return cwd_env
    home_env = Path.home() / ".env"
    if home_env.exists():
        return home_env
    return None
```

This removes a dead search path and makes the behavior easier to explain in the README: **"Put `.env` in your home folder, or in the directory you run the command from."** Two locations, both intuitive.

The script directory fallback only made sense in the old `pip install .` workflow where `__file__` pointed at the clone folder — and even then it was fragile. With `uv tool`, it's pure noise.

Does Python understand where Path.home() is on different operating systems?

---
Yes — `Path.home()` is fully cross-platform. It's been part of Python's `pathlib` since 3.0 and resolves correctly on all three major OSes:

| OS | `Path.home()` returns |
|---|---|
| Linux | `/home/username` |
| macOS | `/Users/username` |
| Windows | `C:\Users\Username` |

Under the hood it checks the right environment variable for each OS — `$HOME` on Linux/macOS, `%USERPROFILE%` on Windows — so you don't have to think about it. This is the recommended way to get the home directory in modern Python, replacing the older `os.path.expanduser("~")` pattern.

Since your `pyproject.toml` requires `>=3.8`, you're well covered. No OS-specific code needed.
